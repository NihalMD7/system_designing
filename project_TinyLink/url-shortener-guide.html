Basics Explained

What is a URL Shortener?

Service takes long URL, return short alias. Map stored. When user visit short link, server look up original, redirect.

Input:  https://example.com/very/long/path?with=many¶ms=here
Output: https://sho.rt/aX3k2p

Base62 Encoding

Base62 = 62 chars: 0-9 + a-z + A-Z. Convert big number into short string. 6 chars Base62 = 62⁶ = ~56 billion combinations. Enough for huge service.

ID 12345 → "3D7"
ID 1000000 → "4c92"
ID 56800235583 → "zzzzzz" (max 6-char value)

Algorithm: repeatedly divide ID by 62, collect remainders, map to char.

Database Index — Why Critical

Without index: DB scan every row (O(n)). 10M rows = slow.

With B-tree index: DB jump straight to row (O(log n)). 10M rows ≈ 23 steps. Microseconds.

-- Slow (no index)
SELECT long_url FROM urls WHERE short_code = 'aX3k2p';
-- 10M rows scanned → 4+ seconds

-- Fast (with index)
CREATE UNIQUE INDEX idx_short ON urls(short_code);
-- Same query → 0.5ms

Cache-Aside Pattern

Read flow: check Redis → if hit, return. If miss, read DB, store in Redis, return.

def get_long_url(code):
    cached = redis.get(code)
    if cached:
        return cached            # HIT: ~1ms
    row = db.query(code)         # MISS: ~5-10ms
    if row:
        redis.setex(code, 3600, row.long_url)
    return row.long_url if row else None

Collision Handling

Two ways generate code:

  • Counter (deterministic): auto-inc ID → Base62. No collisions possible. Predictable URLs (bad for guessing).
  • Random hash: hash long URL or random bytes. Possible collision → catch UNIQUE error, retry with new code.
for attempt in range(5):
    code = random_base62(6)
    try:
        db.insert(code, long_url)
        return code
    except UniqueViolation:
        continue
raise Exception("could not generate unique code")

TTL (Time to Live)

Link expires after N days. Two places set TTL:

  • DB: expires_at TIMESTAMP column. Cron sweep delete expired.
  • Redis: SETEX key ttl_seconds value. Auto-removed.

Idempotency

Same input → same output. POST /shorten with same long URL = should return same short code? Design choice. If yes: store hash(long_url) → check exists before insert.

Schema Example

CREATE TABLE urls (
  id           BIGINT AUTO_INCREMENT PRIMARY KEY,
  short_code   VARCHAR(10) NOT NULL,
  long_url     TEXT NOT NULL,
  created_at   TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  expires_at   TIMESTAMP NULL,
  click_count  BIGINT DEFAULT 0,
  UNIQUE KEY uk_short (short_code),
  INDEX idx_expires (expires_at)

What Breaks If You Skip a Piece

No DB index — 10M rows. Each redirect = full table scan. 4+ seconds per click. Users leave.
No cache — Every redirect hits DB. At 10k req/s the DB cpu maxes out. Service down.
No collision handling — Two users get same code. One URL overwrites other. Data corruption.
No TTL — Storage grows forever. Stale links live forever. Backup time explodes.
No input validation — Attacker submit javascript: URL → stored XSS. Or 1GB URL body → DoS.
No idempotency thought — Same long URL submitted 1M times → 1M short codes → bloated DB.
